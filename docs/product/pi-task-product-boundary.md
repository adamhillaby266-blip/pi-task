# Pi Task 产品主线与边界

> 状态：发布前产品决策。用于约束功能取舍，不替代 Task Framing、Gate C/D/E 的技术与验收合同。

## 一句话定位

Pi Task 是一个以对话为入口，把模糊工作逐渐变成可确认任务，并保留执行、恢复、交付证据和人工验收的本地 AI 工作台。

## 产品目标

用尽可能少的技术设置和用户操作，提高有交付要求的 AI 工作被正确理解、可靠执行、真实验证并由人确认的概率。

“质量”不是流程越多越好；“效率”也不只是首轮回复更快。产品更关注：减少重复解释、方向错误、上下文丢失、返工和无法恢复的执行。

## 用户只需理解的概念

1. **工作目录**：当前对话、文件和任务共同使用的工作范围；
2. **对话**：自由探索和逐渐澄清意图的主入口；
3. **任务约定**：用户确认前只是候选，确认后才成为正式 Task；
4. **执行状态**：正在处理、等待决定、待验收等可理解状态；
5. **交付与验收**：Agent 提交真实产物和验证证据，由用户接受或退回。

Project、SQLite、Session 绑定、Run ID、幂等操作和补偿状态属于内部机制或高级诊断，不应成为普通用户的前置知识。

## 核心路径

```text
选择一个工作目录
→ 自然对话
→ 值得持久交付时形成任务约定
→ 用户保存、确认或确认并开始
→ Pi 在同一对话中执行或等待决定
→ 提交真实产物与验证证据
→ 用户接受或退回
```

普通问答和低风险一次性工作继续保持自由对话，不以 Task 数量作为成功指标。

## 默认自动与必须明确

可以可靠推断的技术细节由系统处理，例如内部目录绑定、Task 版本、Run 恢复和规则发现。

会改变目标、权威来源、权限、外部影响或验收结果的决定必须由用户明确确认。候选约定提供选项时，点击只作为可见用户消息回答当前决定；不直接执行外部操作。产品隐藏技术机制，但不隐藏操作后果。

## 工作纪律

Pi Task 为可写对话提供简短通用纪律：先检查现有结构，采用最小有效修改，保护原始资料，避免无关重组，验证真实成品并报告未验证项。

用户可以通过 Pi 标准 `AGENTS.md` / `CLAUDE.md` 定义个人和工作区规则。界面只显示实际加载来源，不在当前版本自动创建或覆盖规则文件。规则指导 Agent，但不是操作系统沙箱。

## 当前版本明确不做

- 用户侧 Project 创建和独立 Project 选择；
- 通用项目管理、排期、自动认领和团队云协作；
- 完整规则编辑器、AI 自动改规则和规则市场；
- 跨电脑规则或数据自动同步；
- 通用项目文件备份平台和文件级并发写入系统；
- 无人值守多 Agent 或默认开启的多模型编排；
- npm、DMG、Docker、签名应用或托管服务发布。

内部 `projects` 数据继续保留，用于历史兼容、稳定目录关联和交付物范围校验；本次不做破坏性数据库迁移。

## 未来功能准入问题

新增能力前必须回答：

1. 它解决了哪一种真实、重复出现的交付失败？
2. 它是否降低总操作、重复解释或返工？
3. 是否可以由现有对话和上下文安全推断？
4. 它会不会要求用户理解一个新的主概念？
5. 不增加它，核心交付质量是否真的受影响？
6. 如何用真实任务而不是功能数量证明有效？

不能回答这些问题的能力，不进入产品主线。

## 成功判断

- 用户无需先理解 Project 或 Task 表单即可开始；
- 简单对话仍然低摩擦；
- 复杂工作更少因目标、来源和验收不清而返工；
- 中断、退回和重启后可以自然继续；
- Review 包含可检查的产物、验证、风险和未验证项；
- 用户始终保留确认开始、外部影响和最终验收的权力。
