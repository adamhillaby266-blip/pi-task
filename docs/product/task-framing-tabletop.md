# Task Framing 桌面推演

> 状态：产品验证草案，不是实现规格
>
> 数据说明：全部场景与名称均为虚构，不使用真实公司数据
>
> 目标：反向检查“主 Agent 起草任务约定、用户只决定关键问题”的方式，能否同时覆盖代码、数据、报告和设计工作

## 1. 验证问题

本轮不评价 Agent 写得是否漂亮，只检查：

1. 用户能否从一句模糊表达开始；
2. Agent 能否先起草，而不是把表单反问给用户；
3. 阻塞问题是否足够少且确实影响结果；
4. 约定是否能产生真实可执行的验收方法；
5. 哪些内容不能被当前 `goal / acceptanceCriteria / expectedOutput` 三字段充分表达；
6. 哪些工作根本不应被建议任务化。

## 2. 场景 A：数据分析

### 用户初始表达

> 帮我看看本财年的印制成本是不是偏高，找一下主要原因。

### 主 Agent 可直接起草

- **问题方向**：识别本财年印制成本变化及主要驱动因素；
- **可能受众**：生产设计负责人或管理层；
- **建议方法**：先冻结统计口径，再核对总额、期间、重复行和异常项；
- **建议交付**：分析表与简短管理结论；
- **基础验收**：汇总可回溯到权威原表，异常项有来源位置，未确认口径单独标记。

### 不能替用户决定的阻塞问题

1. “本财年”以哪一财年和日期字段计算？
2. 哪份文件是权威来源，是否存在多人维护版本？
3. “偏高”与预算、上一财年、项目均值还是其他基准比较？
4. 是否包含版税、物流或其他非印制费用？

### 不应追问的内容

- 输出文件具体叫什么；
- 使用什么公式或图表；
- 异常检查的常规步骤；
- 是否需要回读公式结果。

这些应由 Agent 提案并在约定中标为建议。

### 反向发现

- 当前 Task 缺少“权威来源”“统计口径”“范围与非范围”的独立表达；
- 验收标准必须由领域 Skill 参与起草，通用模型仅写“准确完整”没有价值；
- 数据任务在来源和口径确认前不能进入 `ready`；
- 精确输出路径不应成为用户的前置负担。

## 3. 场景 B：报告与批示回复

### 用户初始表达

> 根据领导的批示，帮我整理一份正式回复。

### 主 Agent 可直接起草

- **问题方向**：形成一份逐条回应批示要求、可提交给指定受众的正式材料；
- **建议方法**：提取每项要求，区分事实、决定、建议和待确认信息；
- **建议交付**：正式回复文档与批示响应清单；
- **基础验收**：无遗漏要求，数字和规则有来源，措辞符合文种，文档实际渲染无分页和溢出问题。

### 不能替用户决定的阻塞问题

1. 批示原文或权威扫描件在哪里？
2. 最终受众、文种和提交场景是什么？
3. 哪些事项已有明确决定，哪些只能提出建议？
4. 是否存在必须原样引用的数字、日期或规则？

### 不应追问的内容

- 标题层级如何安排；
- 使用什么文件名；
- 是否逐条核对批示；
- 是否检查分页。

### 反向发现

- “受众与使用场景”是合同核心，不应被埋在目标文本中；
- 权威原文缺失时不能由模型凭常识补造；
- 有些任务交付不仅是文件，还包括“逐条响应矩阵”这一验证记录；
- 报告任务的验收包含内容和实际载体两层，不能只检查文字。

## 4. 场景 C：设计与页面

### 用户初始表达

> 把这个任务看板做得更专业一些，现在有点平。

### 主 Agent 可直接起草

- **问题方向**：提高真实页面的信息效率、层级和整体完成度，而不破坏既有功能；
- **建议方法**：先检查真实页面和数据，再识别视觉主角、阅读顺序和关键动作；
- **建议交付**：实际页面改动、关键状态截图和验证记录；
- **基础验收**：真实页面渲染通过，核心交互不回归，长文本、空状态、失败状态和目标尺寸可用。

### 不能替用户决定的阻塞问题

1. “更专业”主要指概念、信息层级、品牌气质还是视觉精度？
2. 哪些信息结构和功能不能改变？
3. 首要使用尺寸和设备是什么？
4. 是否有必须遵守的品牌或参考方向？

### 不应追问的内容

- 使用几列栅格；
- 具体字号和间距；
- 是否需要检查长文本和空状态；
- 如何实现 CSS。

### 反向发现

- 设计任务无法在开始前把所有审美标准写成机械验收项；
- 合同需要允许“关键页面方向闸门”：先确认一个真实页面，再铺开；
- 视觉 Agent 必须能查看真实渲染，只有文本角色画像没有专业价值；
- 验收标准应保护功能与信息结构，而不是只描述风格词。

## 5. 场景 D：代码与发布

### 用户初始表达

> 把 Pi SDK 升级到新版本，确认没问题以后再考虑发布。

### 主 Agent 可直接起草

- **问题方向**：完成版本升级和兼容适配，证明现有对话、模型、Session、取消、恢复和本机运行路径没有回归；
- **权威来源建议**：目标版本官方包、变更日志、现有测试和发布文档；
- **建议交付**：独立代码提交、测试与构建证据、升级报告；
- **基础验收**：类型检查、Lint、测试、生产构建、隔离真实页面和恢复路径通过，安全审计变化可解释。

### 不能替用户决定的阻塞问题

1. 准确目标版本和允许升级的依赖范围是什么？
2. 是否允许真实 Provider 或付费模型调用？
3. 是否允许修改当前安装、LaunchAgent、主分支或公开发布？
4. 哪些兼容行为是发布阻塞项？

### 不应追问的内容

- 使用什么测试命令；
- 是否需要隔离 HOME 和数据目录；
- 是否检查取消与恢复；
- 代码提交如何组织。

### 反向发现

- 高风险权限边界应由合同显式保留，不能只依赖聊天记忆；
- Agent 可以从仓库文档起草大量验收项，用户不应从空白开始；
- “升级完成”和“允许发布”是两个不同决定，合同必须设置阶段门；
- 独立复核应发生在交付前，而不是与实现 Agent 同时泛泛调查。

## 6. 负向场景：不应建议任务化

### 快速措辞修改

> 帮我把这句话说得更直接一点。

单轮即可完成，不需要持久目标、恢复、产物和 Review。主 Agent 不提示任务化。

### 开放讨论

> 我们先聊聊以后团队怎么使用 AI。

用户已明确处于探索阶段。主 Agent 正常讨论；只有在形成明确交付、制度、试点计划或决策材料后，才可低压力建议整理为任务。

### 单一事实查询

> 当前项目使用哪个 Pi SDK 版本？

读取权威文件并回答即可。除非用户进一步要求升级、验证和交付，否则不形成 Task。

## 7. 跨场景结论

### 7.1 统一流程成立

四类任务都可以使用：

```text
Agent 先起草
→ 用户只回答阻塞问题
→ 确认约定
→ 开始执行
```

不需要为每种任务建立独立的任务系统。

### 7.2 通用合同必须与领域方法分层

统一合同负责：

- 目标；
- 受众；
- 权威来源；
- 范围；
- 交付；
- 验收；
- 权限与风险；
- 假设和未决问题。

领域 Skill 负责：

- 数据口径和公式检查；
- 报告文种与逐条回应；
- 设计渲染和交互检查；
- 代码测试、构建和恢复验证。

不应把所有领域规则写入一个巨大的通用 Agent 画像。

### 7.3 当前三字段不足以完整承载约定

现有 `goal / acceptanceCriteria / expectedOutput` 可以继续作为兼容摘要，但无法清楚表达：

- 受众；
- 权威来源；
- 范围与非范围；
- 权限边界；
- 假设；
- 未决问题；
- 阶段门。

这不代表现在应立即迁移数据库。应先冻结用户侧信息结构，再决定采用独立字段、结构化合同对象或兼容投影。

### 7.4 不是所有验收都能一次冻结

数据和代码任务通常可以较早形成较硬的检查；报告和设计任务可能需要中间方向闸门。

因此合同应区分：

- 最终验收标准；
- 执行中的人工判断点；
- 高风险操作确认门。

### 7.5 Task Framing 应优先于多 Agent

四类场景的主要风险首先来自：

- 目标错位；
- 权威来源错误；
- 范围不清；
- 验收不可执行；
- 权限边界遗漏。

增加 Agent 数量不会自动修复这些问题，反而可能并行放大歧义。

## 8. 第一切片需要继续验证的问题

1. 主 Agent 如何生成结构化草案，而不在未确认前写入 SQLite；
2. 如何在不显示复杂表单的情况下编辑草案；
3. 从积压事项进入澄清对话时，是否立即绑定主 Session；
4. 用户选择“确认并开始”后，如何以可见方式形成 Run 起点；
5. 当前三字段与未来丰富合同之间如何兼容；
6. 设计任务的中间方向闸门是否需要独立对象；
7. 决策记录和外部操作回执如何成为可验收产物。

这些问题应在交互合同确认后再进入技术设计。
