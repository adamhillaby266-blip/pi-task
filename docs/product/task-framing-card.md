# 任务约定卡：产品交互合同

> 状态：交互与 Pi Task 视觉基线已于 2026-08-14 通过原型人工检查；Slice A–E 已完成产品实现、审查修正与隔离页面验证；后续单一工作目录减法切片已移除新任务的旧表单入口，历史 Task 的旧字段编辑仅保留为兼容回退
>
> 依赖：`docs/architecture/task-framing.md`
>
> 目标：在 Pi 原生对话中承载任务成形、关键澄清和用户确认，不把用户重新带回高负担表单
>
> 技术设计：`docs/architecture/task-framing-technical-design.md`

## 1. 核心原则

1. 卡片嵌在主 Agent 对话中，不建立独立规划工作台。
2. 主 Agent 先起草，用户只处理会实质影响结果的未决问题。
3. 默认展示摘要和阻塞项，详细合同按需展开。
4. 用户可以自然语言修改，不必逐字段编辑。
5. Agent 建议、假设和用户已确认事实必须视觉可区分。
6. 草案不是权威 Task；只有用户显式保存或确认后才写入 SQLite。
7. 确认任务约定不自动开始 Run；“确认并开始”是单独、明确的执行授权。
8. 保存、准备或启动失败时，不丢失当前草案和用户输入。

## 2. 信息优先级

卡片不是按数据库字段顺序展示，而是按用户决策顺序组织。

### 第一层：当前需要用户做什么

始终位于卡片顶部：

- 草案状态；
- 是否已足够开始；
- 仍有多少项阻塞决定；
- 当前最关键的问题；
- 下一步可执行动作。

### 第二层：一句话任务结果

用户无需展开即可判断 Agent 是否理解正确：

- 任务标题；
- 要解决的问题；
- 受众或用途；
- 建议交付。

### 第三层：完成与风险边界

摘要展示：

- 核心验收项；
- 权威来源状态；
- 明确不做的内容；
- 高风险确认门。

### 第四层：完整约定

展开后显示：

- 要解决的问题；
- 受众与使用场景；
- 权威资料；
- 范围与非范围；
- 预期交付；
- 验收方法；
- 约束与确认点；
- 假设与未决问题。

## 3. 默认卡片结构

```text
任务约定 · 草案 2                         还需决定 2 项

判断本财年印制成本变化的主要原因，
为下一轮预算调整提供依据。

需要你决定
1. “偏高”与预算还是上一财年比较？
2. 是否包含物流费用？

已确认
权威来源：虚构生产成本总表
范围：虚构 FY2025

Agent 建议
交付：分析表＋管理结论
验收：总额回读、异常可追溯、未确认口径单列

[查看完整约定]

[继续讨论]  [保存草稿]  [确认并放入待办]  [确认并开始]
```

内容较长时，不在首屏展示完整条款。用户首先看到误解、阻塞项和下一步。

## 4. 信息可信度表达

使用文字与轻量标记共同表达，不只依赖颜色。

### 已确认

来源于用户明确决定、权威资料或既有项目规则。

### Agent 建议

Agent 提出的交付形式、路径、方法或验证方式，用户可调整。

### 假设

为了让方案可执行而提出的前提。未被用户接受前不能伪装成已确认。

### 待决定

答案会改变目标、权威来源、统计口径、范围、权限、交付或验收。

只有会阻止当前任务安全开始的问题才标记为阻塞决定。未来安装、升级、发送或公开推送等下游授权保留为非阻塞问题或对应 Gate，不提前阻塞当前阶段。

Agent 提供明确选项时，界面把选项渲染为真正的按钮。点击后发送一条可见、可审计的用户消息，由 Agent 更新候选约定；点击本身不写 Task、不开始 Run，也不直接执行外部操作。输入框已有草稿、对话忙碌或工具关闭时必须保护用户输入并说明原因。

不显示虚假的置信度百分比，也不使用“合同质量 87 分”之类评分。

## 5. 状态模型

任务约定卡拥有界面状态，但不增加 Task 业务状态。

### 5.1 候选草案

- 只存在于当前 Session；
- 可能仍有阻塞问题；
- 可以继续讨论或显式保存到 `backlog`；
- 不能直接进入 `ready`，除非所有阻塞项已解决或被用户明确接受为假设。

### 5.2 待用户确认

- Agent 判断已足够安全开始；
- 没有未处理的阻塞决定；
- 用户仍需检查并显式确认；
- Agent 无权自行保存或开始。

### 5.3 已保存草稿

- SQLite 中存在 `backlog` Task；
- 当前 Session 保留草案讨论；
- 用户可以继续自然语言修改；
- 后续确认使用 Task `version` 防止覆盖其他窗口修改。

### 5.4 已确认待办

- Task 为 `ready`；
- 尚无活动 Run；
- 卡片显示“任务约定已确认，尚未开始”；
- 可以继续回看、显式编辑或开始执行。

### 5.5 正在保存或启动

- 锁定重复提交动作；
- 保留草案正文可读；
- 明确说明正在执行的是“保存”“确认”还是“启动”；
- 不使用模糊的统一加载状态。

### 5.6 已取代

当 Agent 根据新输入生成下一版草案时：

- 最新草案保持展开；
- 旧卡片折叠为“已由草案 3 取代”；
- 用户仍可查看旧版本及变化摘要；
- 不在对话中堆叠多个视觉重量相同的大卡片。

### 5.7 已放弃

用户明确表示不任务化时：

- 卡片折叠为普通记录；
- 当前对话继续自由交流；
- 本 Session 不再主动建议任务化，除非用户再次主动提出。

## 6. 四个用户动作

### 6.1 继续讨论

- 不写入 Task；
- 焦点返回输入框；
- 可以直接说“比较上一财年，不含物流”；
- Agent 根据新信息生成下一版草案。

### 6.2 保存草稿

- 创建或更新 `backlog` Task；
- 不准备执行 Session，不创建 Run；
- 成功后显示 Task 入口；
- 保存失败时保留候选草案，并允许重试。

### 6.3 确认并放入待办

- 用户确认当前 Task Contract；
- Task 创建或更新为 `ready`；
- 当前持久 Session 成为主 Session；
- 不创建 Run，不继续执行任务；
- 卡片明确显示“已确认，尚未开始”。

### 6.4 确认并开始

- 用户同时确认 Task Contract 和本次执行；
- 系统创建或更新 `ready` Task，再原子开始 Run；
- 开始动作必须作为可见用户事件进入 Session 与 Task Event；
- 如果 Task 已保存但 Run 启动失败，Task 保持 `ready`，显示恢复入口，不伪造 `in_progress`。

## 7. 自然语言修改

自然语言是默认编辑方式。

示例：

> 财年按 2025 年 4 月到 2026 年 3 月，不含物流；给总经理办公会看。输出先做管理摘要和异常明细。

主 Agent 应：

1. 提取明确决定；
2. 更新对应条款；
3. 标记此前假设是否被确认或推翻；
4. 只追问剩余阻塞问题；
5. 给出草案变化摘要。

卡片可以提供“编辑完整约定”作为辅助入口，但不能要求用户逐字段保存才能继续。

## 8. 主动建议策略

主 Agent 只有在任务化信号明显时建议一次。

### 建议出现的条件

- 当前 Session 已持久化；
- 尚未绑定其他主 Task；
- 用户没有声明“先聊聊”“先别做”或类似探索意图；
- 工作呈现正式交付、跨回合、验证、恢复或高风险特征；
- 本 Session 尚未拒绝过任务化建议。

### 不应出现

- 对话刚开始、信息极少；
- 简单问答或快速措辞修改；
- Agent刚刚回答错误、尚未修复；
- 用户正在处理更紧急的确认或错误；
- 当前 Session 已绑定 Task。

建议本身不创建草案、不调用额外模型，只提供“一起聊清楚”入口。

## 9. 异常与恢复

### 9.1 草案结构生成失败

- 回退为普通文本摘要；
- 不显示空白或错误字段；
- 提供“重新整理”动作；
- 不写入 SQLite。

### 9.2 Session 尚未持久化

- 可以继续讨论候选约定；
- 保存前先完成正常 Session 持久化；
- 持久化失败时不创建孤立 Task。

### 9.3 当前 Session 已绑定其他 Task

- 不允许创建第二个主 Task；
- 显示当前绑定任务；
- 如讨论产生另一个任务，后续应通过显式拆分流程处理，第一切片不自动拆分。

### 9.4 工作目录尚未建立内部关联或范围不匹配

- 用户只确认当前工作目录，不选择或新建独立 Project；
- 保存时系统自动复用最具体的兼容内部 Project，或为当前目录登记兼容记录；
- 服务端继续验证真实 Session、空闲状态和内部根目录包含关系；
- Agent 不能通过草案绕过工作范围。内部 Project 仅用于历史兼容，不成为用户概念。

### 9.5 版本冲突

- 不覆盖其他窗口保存的 Task Contract；
- 回读最新版本并显示差异；
- 保留本地草案，交给用户决定合并或放弃。

### 9.6 保存成功、准备失败

- 明确说明 Task 已保存；
- 保持 `backlog` 或 `ready` 的权威状态；
- 提供从 Task 或当前 Session 重试的入口；
- 不要求用户重新整理合同。

### 9.7 Run 启动失败

- 已确认 Task 保持 `ready`；
- 没有活动 Run 或幽灵 `in_progress`；
- 记录恢复原因；
- 用户可在同一 Session 再次明确开始。

## 10. 移动端与可访问性

- 未决问题和主动作必须在移动端首屏可见；
- 四个动作在窄屏按重要性纵向排列，不压缩成难以点击的小按钮；
- 所有状态同时使用文字，不只用颜色和图标；
- 展开、折叠和确认支持键盘操作；
- 长目标、长来源路径和验收条件允许换行，不横向溢出；
- 保存与启动时保持可读，不用整卡骨架屏覆盖内容。

## 11. 第一切片的状态覆盖

实现前至少冻结并验证以下真实页面状态：

1. 初次候选草案，存在阻塞问题；
2. 用户自然语言补充后的第二版草案；
3. 已足够开始、等待确认；
4. 已保存 `backlog`；
5. 已确认 `ready`，尚未开始；
6. 正在保存；
7. 保存失败但草案仍在；
8. 版本冲突；
9. 保存成功但 Session 准备失败；
10. 确认并开始失败后恢复为 `ready`；
11. 用户拒绝任务化；
12. 长文本和移动端布局。

## 12. 验证标准

- 用户不需要从空白字段开始；
- 首屏可以看出 Agent 是否理解了真正目标；
- 首屏可以看见所有阻塞问题；
- Agent 建议不会伪装成用户决定；
- 用户可以只用自然语言完成修改；
- 保存、确认和开始是三个可区分后果；
- 任一失败路径都不丢草案、不产生幽灵 Run；
- 卡片不会压过主对话，旧草案不会堆满消息流；
- 不任务化的普通对话保持原有低摩擦体验。

## 13. 尚未进入的技术决策

以下问题留到产品交互合同确认后处理：

- 候选草案使用哪种 Pi 自定义消息或工具结果承载；
- 丰富合同采用独立字段、JSON 对象还是兼容投影；
- 草案版本如何映射 Session 历史；
- `backlog` 澄清 Session 何时建立主绑定；
- “确认并开始”如何与现有发送前 `beginRun` 路径兼容；
- 非文件 Artifact 如何建模；
- 中间方向闸门是否成为独立对象。
