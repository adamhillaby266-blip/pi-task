# Task Framing：从自由对话形成任务约定

> 状态：产品方向与任务约定卡交互已确认；技术设计见 `docs/architecture/task-framing-technical-design.md`；Slice A–E 已合入并完成本机真实升级验收；后续单一工作目录减法切片已完成隔离实现与验证，尚未合入或安装
>
> 适用范围：Pi Task 的自由对话、积压事项、待办事项与 Run 启动路径
>
> 核心目标：降低正式任务的定义门槛，提高后续执行、复核和交付质量，而不是增加 Task 数量或追求自动执行速度

## 1. 决策摘要

Pi Task 在增加独立复核、并行调查和跨模型会诊前，先补齐 `Task Framing`（任务成形）能力。

用户界面使用“任务约定”和“一起把任务聊清楚”；底层与架构文档继续使用 `Task Contract`。

已确认的产品决定：

1. 自由对话负责探索，任务约定代表正式承诺，Run 负责执行，Review 负责交付。
2. 用户不从空白表单独自编写目标、验收条件和预期产物；主 Agent 根据当前对话先起草。
3. 主 Agent 只追问会实质改变目标、范围、权威来源、权限或结果的问题。
4. 主 Agent 可以克制地建议任务化，但不能擅自创建 Task、确认合同或开始 Run。
5. 用户拒绝一次任务化建议后，本次对话不重复提示。
6. 确认任务约定不等于自动执行；只有显式选择“确认并开始”才构成执行授权。
7. 第一产品切片只完成任务成形，不同时加入独立复核、并行 Agent 或跨模型会诊。
8. 当前只读多 Agent 代码是受控子执行的技术验证，不代表最终产品入口、角色体系或流程合同。

## 2. 问题与真实使用证据

当前实现要求 `ready` Task 至少具备：

- 目标；
- 验收条件；
- 预期产物。

系统能够保证合同完整性、目录边界、单一活动 Run、Review 和人工验收，但把合同起草工作主要交给了用户。

一周真实使用中，Task 模式只被使用一次，其他工作仍以自由对话完成。当前反馈表明，主要阻力不是看板操作，而是复杂工作的目的、范围、交付形式和验收标准往往需要通过讨论才能逐渐明确。

这与 Gate D 已记录的未决问题一致：是否应使用当前模型辅助整理任务合同。真实使用现已支持肯定答案。

## 3. 产品定位

Task Framing 不是：

- 新的规划 Agent；
- 多 Agent 头脑风暴；
- 表单自动填充器；
- 可视化工作流编辑器；
- 在用户不知情时创建任务或调用额外模型。

Task Framing 是主 Agent 与用户在原生对话中共同完成的最小可执行约定。

```text
自由对话
  → 识别正式交付价值
  → 主 Agent 起草任务约定
  → 解决少量关键未决问题
  → 用户确认
  → 保存草稿 / 放入待办 / 明确开始
```

## 4. 适用条件

Task 数量不是成功指标。只有当工作需要持久目标、恢复、交付和验收时，才值得任务化。

适合建议任务化的信号：

- 存在正式交付物或需要留存的决定；
- 可能跨多个回合、多个小时或多次会话；
- 有明确受众、截止要求或业务用途；
- 失败代价较高；
- 需要权威来源、验证证据或退回修改；
- 用户开始讨论范围、数据、权限、发布或交付要求。

不建议任务化：

- 简单问答；
- 一次性措辞修改；
- 尚无明确方向的开放闲聊；
- 不需要产物、恢复或验收的低风险操作。

主 Agent 的建议应低压力、一次性：

> 这件事已经涉及明确交付和验收，要不要先一起整理成任务约定？我先起草，不会自动执行。

## 5. 两条入口

### 5.1 从自由对话形成 Task

1. 用户先用自然语言讨论问题。
2. 用户主动要求整理为任务，或接受主 Agent 的一次性建议。
3. 主 Agent 使用当前对话、已读取的权威资料和已确认决定生成约定草案。
4. 主 Agent 只询问阻塞性问题。
5. 用户确认后，当前持久 Session 成为 Task 的主 Session。
6. 未选择“确认并开始”时，不创建 Run，不调用模型继续执行。

### 5.2 从积压事项继续澄清

1. 用户可以只用标题或不完整描述创建 `backlog` Task。
2. Task 详情提供“和 Pi 一起补全”。
3. 系统打开或恢复一个合同澄清对话，但不启动 Run。
4. 主 Agent 起草并更新约定草案。
5. 用户确认后，Task 才能进入 `ready`。

两条入口最终产生同一种 Task Contract，不建立两套任务协议。

## 6. 任务约定的信息结构

用户不面对大量空白必填框。主 Agent 应先提供一张完整度可见的草案。

### 6.1 要解决的问题

描述最终要改变什么、回答什么，或支持什么决定。避免只写“整理”“分析”“优化”等活动词。

### 6.2 受众与使用场景

说明谁使用结果，以及结果用于汇报、决策、执行、发布还是留档。

### 6.3 权威资料

列出事实、数据和规则以什么为准。无法确认时明确标注来源策略或阻塞项，不由模型猜测。

### 6.4 范围与非范围

说明本次工作包含什么、不包含什么，以及当前工作目录、时间、对象和权限边界。

### 6.5 预期交付

可以是文件、表格、报告、页面、决策记录或外部操作回执。Agent 可以建议载体和路径，用户不必预先知道准确文件名。

### 6.6 验收方法

使用可观察、可复核的标准，包括内容正确性、载体质量、异常路径和未验证部分。避免“内容完整”“质量良好”等不可验证表述。

### 6.7 约束与确认点

列出不可改动的原始资料、数据外发边界、真实安装、删除、发送、发布等需要再次确认的操作。

### 6.8 假设与未决问题

允许任务在显式假设下开始，但不能隐藏会实质改变结果的未决问题。

## 7. 信息可信度标记

草案中的内容必须区分：

- **已确认**：来自用户原话、权威资料或既有决定；
- **Agent 建议**：交付形式、输出路径、检查方法等可调整方案；
- **假设**：为了形成可执行方案而提出、需要用户接受的前提；
- **待决定**：未解决前会实质改变结果或权限的事项。

Agent 不得把推断静默写成已确认事实。

## 8. 最少必要提问原则

主 Agent 应先尽可能起草，再提问。只有以下问题值得阻塞确认：

- 答案会改变任务目标；
- 答案会改变权威数据或统计口径；
- 答案会扩大项目或隐私边界；
- 答案会改变最终交付载体；
- 不确认就无法制定真实验收方式；
- 不确认可能导致不可逆或高风险操作。

普通实现细节、建议路径和常规检查方式应由 Agent 提案，不转嫁给用户。

## 9. 合同就绪判断

不使用易被模型迎合的数字评分。界面显示可理解的检查结果：

- 目标是否明确；
- 权威来源是否确认或有可接受策略；
- 范围是否足够清楚；
- 交付形式是否明确；
- 验收是否可实际执行；
- 是否仍有阻塞性决定；
- 高风险动作是否有确认门。

进入 `ready` 的标准是“足以安全开始”，不是提前知道全部执行细节。

## 10. 用户操作与权限边界

任务约定卡提供四个明确操作：

### 继续讨论

只修改对话中的候选草案，不写入正式 Task 状态。

### 保存草稿

显式创建或更新 `backlog` Task。不得因为 Agent 生成了草案而自动保存。

### 确认并放入待办

用户确认 Task Contract，Task 进入 `ready`；不创建 Run，不自动发送任务提示，不继续调用模型执行。

### 确认并开始

这是独立、显式的执行授权。系统可以确认 Task Contract、创建 Run 并在当前主 Session 中开始，但必须留下可见的用户动作和状态事件，不得伪装成 Agent 自主开始。

主 Agent 无权：

- 代替用户确认任务约定；
- 自行把 `backlog` 移入 `ready`；
- 自行开始 Run；
- 接受 Review；
- 将 Task 标记为完成。

## 11. 与现有状态机的关系

Task Framing 不要求新增业务状态：

```text
自由对话
  → 候选约定（仅在 Session 中）
  → backlog（显式保存的草稿）
  → ready（用户已确认，尚未自动执行）
  → in_progress（用户已明确开始，存在活动 Run）
  → in_review（Agent 已提交交付）
  → done（用户已验收）
```

当前 `ready` 的语义保持为“可执行”，而不是后台调度队列。

## 12. 执行中的合同变化

- 不改变目标、范围或验收口径的普通澄清，可以作为当前 Run 的补充输入。
- 会实质改变目标、来源、范围、权限或验收标准的变化，必须暂停当前 Run，形成新的合同版本，再由用户确认后开始新 Run。
- 重要决定不能只埋在聊天记录中；应进入 Task Contract、恢复说明或 Review 记录。

## 13. 非文件型交付

当前实现要求 Review 至少包含一个项目内真实文件，这使 Task 更适合代码、报告、表格和设计文件。任务成形会暴露决策、审批、外部操作等非文件型交付需求。

第一切片先记录这些需求，不在 Task Framing 中顺带重构 Artifact。后续需要单独决定是否支持：

- Task 内部决策记录；
- URL 或外部对象；
- 操作回执；
- 渲染截图或验证快照；
- 自动生成的交付摘要。

## 14. 与多 Agent 的关系

Task Framing 由用户和主 Agent完成，不使用多个子 Agent讨论用户意图。

后续多 Agent只在已确认合同下工作：

1. **独立复核**：检查 Task Contract、权威来源、真实产物和验证证据；
2. **分域调查**：在可独立拆分的资料范围内并行收集证据；
3. **跨模型会诊**：对高风险争议进行显式、受预算和数据政策约束的多模型判断。

没有清楚 Task Contract 时，不启动多 Agent，避免并行放大歧义。

## 15. 第一产品切片

第一切片只验证任务成形：

1. 从当前对话生成任务约定草案；
2. 区分已确认、建议、假设和待决定；
3. 支持少量澄清迭代；
4. 提供继续讨论、保存草稿、放入待办和确认开始四种明确动作；
5. 保持原 Session；
6. 不自动启动、不增加多 Agent调用；
7. 为积压 Task 提供“和 Pi 一起补全”的入口。

暂不包含：

- 独立复核；
- 并行 Agent；
- 每个 Agent 的独立模型选择；
- Agent/Skill 市场；
- 工作流编辑器；
- 自动调度。

## 16. 验证方法

先用代表性、非敏感任务做桌面推演，再决定实现：

- 代码与自动化：升级、发布或恢复检查；
- 数据分析：口径、来源、异常和输出；
- 报告与制度：受众、权威要求、逐条回应和渲染；
- 设计与页面：真实页面、数据、交互状态和验收尺寸。

实现后的真实使用验证关注：

- 用户是否能从模糊描述自然形成 Task；
- Agent 是否减少了空白填写负担；
- 用户是否仍需修正大量关键假设；
- Run 中发生实质范围变更的频率；
- Review 因目标或验收缺失被退回的情况；
- Task 是否用于原本需要交付、恢复和验收的复杂工作。

不以 Task 创建数量或多 Agent 调用次数作为成功指标。

## 17. 后续顺序

1. 完成任务成形产品验证；
2. 经过真实任务使用后冻结交互合同；
3. 实现一个独立只读复核者；
4. 再开放分域并行；
5. 最后研究按能力、成本和数据政策分配不同模型。
